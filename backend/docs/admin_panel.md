# Админ-панель (Filament v3)

Веб-интерфейс для операторов: управление организациями, событиями, источниками, справочниками, статьями и связями. Публичное API (`/api/v1/…`) и внутренний import API (`/api/internal/…` с Bearer) **не заменяются** — админка дополняет их для ручных сценариев.

## URL и доступ

- Панель: **`/admin`** (относительно `APP_URL`).
- Доступ только у пользователей с **`users.is_admin = true`**.
- Сессии используют стандартный Laravel `web` guard (как настроено в Filament).

## Первый администратор

После применения миграций:

```bash
php artisan admin:create your@email.example 'secure-password-here'
```

- Если пользователь с таким email уже есть — ему выставляется `is_admin`, пароль обновляется.
- Новому пользователю задаётся `email_verified_at` (см. модель `User`).

## Данные, БД и API

- Админка **не ходит в REST API**: списки и формы используют **Eloquent** и **тот же** default-подключение к БД, что и остальное приложение (`config/database.php`, переменные `DB_*` в `.env`).
- Публичное API и internal import API пишут в **те же таблицы** (при той же конфигурации). Если обход/импорт ещё не заполнял БД или вы смотрите **другую** БД (другой `.env`, sqlite локально vs Postgres на сервере), в админке будут пустые списки и нули на дашборде — это не «обрыв связи», а отсутствие строк в таблицах.
- После `migrate` без сидов/дампа таблицы организаций, событий, источников и т.д. часто **пустые**. `DatabaseSeeder` по умолчанию создаёт в основном справочники и тестового пользователя (см. `database/seeders/DatabaseSeeder.php`), но не массовые демо-организации.
- На дашборде счётчики — обычные `Model::query()->count()`. Виджет **Organizations in review** показывает только строки со `status = in_review`; при пустой таблице он пустой. **Recently crawled sources** — только с заполненным `last_crawled_at`.

Проверка среды (из каталога `backend/`):

```bash
php artisan db:show
php artisan tinker --execute="echo 'users='.\App\Models\User::count().' orgs='.\App\Models\Organization::count();"
```

## Навигация (группы меню)

- **Entities** — организации, события, организаторы, площадки, физлица, инициативные группы.
- **Content** — статьи (контент в **Markdown**).
- **Dictionaries** — тематические категории, услуги, типы и формы собственности, уровни охвата, профили специалистов, категории событий, целевая аудитория.
- **Harvester** — источники, профили парсинга, предложения таксономии (LLM), экземпляры событий.
- **System** — пользователи (`UserResource`: в т.ч. флаг администратора).

## Типовые сценарии

### Новая организация

1. Проверить дубликаты: при вводе ИНН/ОГРН на форме создания показываются подсказки со ссылкой на существующую запись.
2. Заполнить карточку, секцию **Organizer**, привязки к справочникам.
3. Площадки и источники — через вкладки **Relation managers** у организации или через ресурсы Venue / Source (привязка к организатору).

### Событие

Создание/редактирование в **Events**; площадки и расписание (instances) — relation managers на карточке события.

### In review после LLM

- Табы **In review** в списках организаций и событий.
- Ресурс **Suggested taxonomy items** — фильтры по статусу и типу словаря, массовое approve/reject.

### Результаты обхода источников

- **Sources**: сортировка по `last_crawled_at`, фильтр по диапазону дат, табы Active/Inactive.
- Дашборд: виджет недавно обходимых источников.
- Детализация изменений по сущностям — вручную по `updated_at` и переходам к связанным организациям/событиям.

### Статья

**Articles** — поле контента через Markdown-редактор Filament; slug можно заполнить вручную или получить из заголовка при первом сохранении (если slug пуст).

## Пользователи в панели

Администратор может создавать пользователей в **System → Users** и выдавать им `is_admin`. Удаление **своей** учётной записи из таблицы заблокировано в действии строки (bulk-delete не фильтрует текущего пользователя — осторожность при массовом удалении).
