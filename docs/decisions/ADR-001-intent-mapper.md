# ADR-001: Реализация Intent Mapper для Navigator Core

## Статус
Предложено (требуется обсуждение)

## Контекст
Фронтенд Navigator Core нуждается в механизме маппинга пользовательских интентов (текстовых запросов) на фильтры API для реализации концепции "Ответ вместо поиска" (Answer Instead of Search). 

**Проблема**: Пользователь вводит "помощь при деменции" → фронтенд должен преобразовать это в:
- `thematic_category_id=7` (Снижение памяти и деменция)
- `service_id=116` (Система долговременного ухода)
- Возможно, другие параметры фильтрации

**Требования**:
1. Минимальная задержка (не более 100-200мс)
2. Работа в оффлайн-режиме (мини-приложения)
3. Простота обновления правил
4. Поддержка синонимов и разговорных формулировок

## Варианты решения

### Вариант A: Статический JSON на фронтенде
**Описание**: Фронтенд загружает JSON-файл с правилами маппинга при инициализации.

**Структура данных**:
```json
{
  "intents": [
    {
      "patterns": ["деменция", "потеря памяти", "проблемы с памятью"],
      "filters": {
        "thematic_category_id": [7],
        "service_id": [116]
      }
    },
    {
      "patterns": ["сиделка", "уход за пожилым", "помощь на дому"],
      "filters": {
        "service_id": [81, 82]
      }
    }
  ]
}
```

**Плюсы**:
- Нулевая задержка (все вычисления локальные)
- Работает оффлайн
- Нет нагрузки на бэкенд
- Простота реализации

**Минусы**:
- Нужно обновлять приложение для изменения правил
- Ограниченная "интеллектуальность" (только точные совпадения)
- Дублирование логики на клиенте

### Вариант B: Серверный эндпоинт `GET /v1/intent`
**Описание**: Фронтенд отправляет запрос на сервер, который возвращает фильтры.

**API**:
```
GET /api/v1/intent?q=помощь+при+деменции
```

**Ответ**:
```json
{
  "query": "помощь при деменции",
  "filters": {
    "thematic_category_id": [7],
    "service_id": [116]
  },
  "confidence": 0.95,
  "suggested_title": "Организации, помогающие при деменции"
}
```

**Плюсы**:
- Централизованная логика
- Можно использовать LLM/нейросети для сложных случаев
- Легко обновлять правила
- Можно добавлять аналитику

**Минусы**:
- Зависимость от сети
- Дополнительная нагрузка на сервер
- Задержка сети

### Вариант C: Гибридный подход
**Описание**: Основные правила на клиенте + fallback на сервер для сложных случаев.

**Реализация**:
1. Клиент проверяет локальный кэш правил
2. Если нет точного совпадения → запрос на сервер
3. Сервер может обновлять кэш клиента

**Плюсы**:
- Быстрая работа для частых запросов
- Гибкость для сложных случаев
- Можно постепенно улучшать

**Минусы**:
- Наиболее сложная реализация
- Нужна синхронизация кэша

## Рекомендация

**Рекомендуется Вариант A (Статический JSON)** для MVP по следующим причинам:

1. **Срочность**: Нужно решение "вчера", фронтенд не может ждать разработки серверной части
2. **Простота**: Можно реализовать за 1-2 дня
3. **Надежность**: Не зависит от сети/сервера
4. **Масштабируемость**: Позже можно мигрировать к Варианту B/C без изменения API фронтенда

**План реализации Варианта A**:

1. **Backend**: Создать эндпоинт для генерации JSON:
   ```
   GET /api/internal/intent-rules
   ```
   Возвращает актуальные правила в формате для фронтенда.

2. **Frontend**: 
   - Загружать `intent-rules.json` при старте приложения
   - Реализовать простой matcher (по ключевым словам)
   - Кэшировать в localStorage

3. **Обновление правил**:
   - При каждом запуске приложения проверять хэш файла
   - Если изменился — загружать новую версию

## Последствия

### Положительные
- Быстрый запуск MVP
- Минимальные изменения в Core
- Независимость от сети

### Отрицательные
- Нужно перевыпускать приложение для обновления правил
- Ограниченная "интеллектуальность"

## Дальнейшие шаги

1. **Совещание**: Обсудить с командой фронтенда
2. **Прототип**: Реализовать JSON-файл с 10-20 основными интентами
3. **Интеграция**: Добавить эндпоинт в Core для генерации правил
4. **Мониторинг**: Собирать аналитику по использованию интентов
5. **Эволюция**: Планировать переход к Варианту B при росте сложности
